# bbridge protocol overview (draft)

*Draft for internal iteration. Describes the target architecture as it was being worked out. Most of what §9 below originally flagged as a gap is now implemented — see [`docs/SPEC.md`](SPEC.md) for the current, consolidated specification (message formats, the `mintCovenantV2` self-mint covenant, decimal scaling) and [`contracts-spec.md`](contracts-spec.md) for the Ethereum contract's own design log. This document is kept for the reasoning behind the original design, not as a description of current state — where it still diverges from what was actually built, that's noted inline rather than silently left inconsistent.*

## 1. Scope and relationship to other documents

This document describes the technical architecture of the XEC ↔ Ethereum bridge: the actors, the on-chain components, and the lifecycle of a deposit and a withdrawal. It is derived from the description of the system in the no-action-letter application draft (the "legal description") and from the primitives already built in `packages/sdk`.

Two things this document is *not*:

- It is not legal advice, and does not itself make any legal determination. Where a design choice here is load-bearing for the legal description's argument (most importantly, the Authorizer's lack of discretion), that's called out explicitly, but the legal analysis itself lives in the no-action-letter draft, not here.
- It is not yet a byte-level wire-format spec. Exact OP_RETURN layouts, ABI signatures, and script opcodes belong in follow-on documents (e.g. an XEC data-format spec, an Ethereum contract spec) once the design here is settled. This document is the architecture those will implement.

This is a **draft**. Where the legal description underdetermines an implementation choice, or where an existing `packages/sdk` primitive doesn't fit the design described here, that's flagged rather than silently resolved — those are exactly the points this document exists to surface for discussion before more code gets written.

## 2. Actors and components

- **User** — locks value on Ethereum, receives (and later redeems) a wrapped representation on XEC. The only party that ever signs a transaction moving their own funds, on either chain.
- **Authorizer** — confirms that a deposit occurred, so that a corresponding quantity of wrapped token can become mintable. Never takes custody of user funds. Never signs a transaction on the user's behalf. Its role is intentionally narrow — see §4.
- **Ethereum lock contract** — an immutable, non-upgradable contract with no admin key. Holds locked collateral, tracks deposits and confirmations, and holds the sole authority to compute deterministic authorization content and release collateral against a valid burn proof.
- **eCash self-mint covenant ("mint vault")** — a P2SH-covenant-locked UTXO on XEC that enforces: a mint transaction spending it may only produce outputs matching content the Authorizer's key validly signed. The covenant, not any party's discretion, is what prevents minting outside what was authorized.
- **Wrapped token** — an SLP token on XEC, 1:1 backed by the net (post-fee) amount locked on Ethereum.

## 3. Design invariants

These carry over directly from the legal description's key representations (§1.3 of the no-action-letter draft) and constrain every design choice below:

1. At no point does the Applicant, the Authorizer, or any affiliated party take possession, custody, or control of a user's funds, on either chain.
2. No party other than the user ever signs or broadcasts a transaction that transmits the user's value, on the user's behalf, at any stage, in either direction. (The Authorizer does sign an input of the withdrawal transaction described in §6 — but that input is the Authorizer's own fee-covering UTXO, not the user's tokens. The output that actually burns the user's value is signed exclusively by the user. This distinction is worth flagging explicitly for legal review once this design is finalized, since it's the kind of nuance that matters for this invariant's framing.)
3. The Authorizer's only role is to reference a single-use nonce and provide a signature over content it does not choose — the content is computed independently by the Ethereum contract from already-public, already-finalized deposit data. The Authorizer cannot make that computed content come out differently by choosing a different nonce.
4. The Ethereum lock contract is immutable and non-upgradable, with no administrative override.
5. Any protocol fee is fixed at deployment, applied uniformly, and collected atomically within the user's own transaction — never something a party can alter or apply selectively after the fact.

Two further invariants, not stated explicitly in the legal description but necessary to actually build it, worked out over the course of designing this system:

6. **A deposit can be authorized at most once.** Enforced by the Ethereum contract: a confirmation call is keyed to the specific deposit it attests to, and a second confirmation attempt for an already-authorized deposit is rejected outright, regardless of what nonce is presented.
7. **An authorization can be redeemed into a mint at most once.** Enforced on XEC, not Ethereum: the nonce the Authorizer signs over must be a real, spendable eCash UTXO, and the mint transaction must actually consume it. eCash's native double-spend rule then does the rest — no separate bookkeeping needed.

## 4. Lifecycle: genesis (one-time setup)

The wrapped token is an [SLP Token Type 2](https://github.com/badger-cash/slp-specifications/blob/master/slp-token-type-2.md) token. Type 2 replaced Type 1's single-UTXO "MINT Baton" model with a **MINT Vault** model specifically to remove the serialization Type 1 imposed: under Type 1, only one designated UTXO could ever authorize a mint at a time, so mints had to happen one at a time, each one passing a single baton to the next. Under Type 2, *any* UTXO sitting at the P2SH address named in the GENESIS transaction's `mint_vault_scripthash` field can authorize a mint, and there is no requirement to recreate or pass anything forward — this is precisely what makes concurrent, unserialized mints possible, which matters once deposits are no longer processed one at a time through a single Authorizer-broadcast eCash transaction (see §9).

Before any bridging can occur for a given asset:

1. The wrapped SLP token is deployed via a standard SLP `GENESIS` transaction on XEC, establishing its ticker, name, decimals, document hash, and `mint_vault_scripthash` (the self-mint covenant's own P2SH scripthash, parameterized by the Authorizer's public key).
2. Per the Type 2 specification, a MINT transaction is only valid if it appears in a block *after* the block containing its GENESIS transaction — a MINT in the same block as, or before, GENESIS is invalid. The first deposit for a newly-deployed asset can't be minted until GENESIS has actually confirmed, not merely broadcast.
3. The vault address needs to hold enough independently-spendable UTXOs for however many mints need to happen concurrently. Unlike Type 1's baton, nothing in the protocol *requires* a mint to replenish the vault — that's a funding-strategy choice, not a consensus requirement. Two reasonable approaches: batch-fund the vault ahead of time with many dust-sized UTXOs, or have each mint transaction include an extra output back to the vault address as its own change (Type 2 explicitly allows multiple outputs on a MINT transaction, unlike Type 1 — see §9). Either way, invariant 7 (no double-redemption) still holds purely because each individual UTXO can only be spent once, regardless of how many coexist in the vault at a time.

   **Whichever approach is used, it must respect vault UTXO quarantine** (`docs/SPEC.md` §III.7, added after an audit finding on the confirm/refund race, §7 below). Any vault UTXO funded specifically to back a not-yet-confirmed deposit's authorization must not be broadcast to XEC until that deposit's Ethereum confirmation has reached finality — otherwise a depositor who observes the Authorizer's still-pending confirmation signature (e.g. in Ethereum's public mempool) can front-run it with `refund()` and still complete an unbacked mint with the already-valid signature, since the signature's validity never depended on the Ethereum call succeeding. For batch pre-funding specifically, this means an entire batch must stay withheld until *every* confirmation referencing an output of that batch has landed, not just the first one to confirm.

This part of the design is close to what `packages/sdk` already implements (`buildGenesisTx`, `TOKEN_INFO`, `mintOutscript`); the main gap is that nothing yet funds the vault with more than the single UTXO genesis itself creates (see §9).

## 5. Lifecycle: deposit (Ethereum → XEC)

1. **Lock.** The user sends USDC/USDT to the Ethereum lock contract. The contract deducts its fixed fee and records the net amount and the user's intended XEC recipient.
2. **Refund window.** Before confirmation, the user may unilaterally reclaim the full locked amount using only their own deposit key. No cooperation from the Authorizer or anyone else is required or possible.

   **As actually implemented** (`docs/SPEC.md` §III.2, added 2026-07 as defense-in-depth alongside the vault UTXO quarantine requirement discussed in step 4 below): reclaiming is a two-step handshake, not a single call. The user first calls `requestRefund()`, which records intent and starts a deployment-fixed `refundDelay`-block cooldown but moves no funds; only once that cooldown elapses does `refund()` itself succeed. A live request can be withdrawn via `cancelRefundRequest()`. The point is to give the Authorizer's own monitoring an observable, bounded warning window before a refund can actually be collected — something a single-step refund never provided, since its front-run was instantaneous and unannounced. This narrows the practical window for the race described in step 4 below, but it is not a substitute for quarantine: it depends on the Authorizer actually watching for it, and does nothing for a signature already extracted before any request was made.
3. **Confirmation.** Once the deposit reaches a fixed, uniformly-applied confirmation-depth threshold, the Authorizer submits a confirmation call to the Ethereum contract, supplying only: a reference to a single-use eCash UTXO (see invariant 7), and a signature.
4. **Deterministic content computation.** The contract independently computes the expected authorization content — recipient script, net amount, *and the UTXO reference supplied in step 3* — directly from the deposit it already recorded in step 1 plus that reference. It validates the Authorizer's signature against that computed content, not against anything else the Authorizer submitted. If the signature doesn't match, the call reverts. This computation closes the refund window from step 2.

   The UTXO reference has to be part of the signed content, not just data carried alongside the signature. If the signature only covered recipient and amount, it would say nothing about *which* vault UTXO it authorizes spending — the same signature could then be replayed to redeem the same content against multiple different vault UTXOs, which breaks invariant 7 (redeemed at most once). Binding the reference into what's actually signed is what makes it a single-use nonce rather than an unconstrained side-channel.

   **As actually implemented** (`docs/SPEC.md` §III.4), the signed content is `depositId || utxoTxid || utxoIndex || txOutputs` — the *fully serialized* expected mint outputs, following the [SLP self-mint protocol](https://github.com/badger-cash/slp-self-mint-protocol)'s Token Type 2 authorization format, not the compact `(recipient script, net amount)` fields this paragraph describes. `depositId` in particular was added after this draft was written, in response to an external audit finding: without it, a signature valid for one deposit could be replayed onto a second, unrelated deposit sharing the same recipient and amount. See `contracts-spec.md` §2.3–2.4 for the two corrections this required.

   **A further audit finding (2026-07 review) on this same step:** binding `depositId` and the UTXO reference into the signed content stops the signature from being *replayed* onto a different deposit or vault UTXO — but it does nothing about the signature simply becoming observable *before* step 4 actually completes on Ethereum. The Authorizer's signature is valid the instant it's produced, independent of whether the `confirmDeposit()` call carrying it ever mines. If the vault UTXO it references already exists and is spendable on XEC at that point, a depositor who reads the signature out of Ethereum's public mempool can front-run the pending confirmation with step 2's refund, collect their money back, and still use the untouched signature to mint on XEC — an unbacked mint, since the refund already returned the collateral that mint was supposed to represent. This is closed by an operational requirement on the Authorizer, not a change to what's signed: vault UTXO quarantine (`docs/SPEC.md` §III.7) — the referenced UTXO must not be broadcast to XEC until the Authorizer has independently observed the confirmation reach Ethereum finality. See §4 above and §7 below.
5. **Publication.** The contract exposes `{content, signature}` via a public view function, keyed by the deposit. Anyone — not just the depositing user — can query it; the Authorizer does not deliver or negotiate it with anyone.
6. **Mint.** The user (or anyone acting on the user's behalf, since nothing here requires the user's own key) takes `{content, signature}` from the contract and constructs an XEC transaction spending the specific vault UTXO referenced in step 3 (any UTXO currently sitting at the vault's P2SH address is eligible — see §4). The self-mint covenant verifies the Authorizer's signature against the supplied content, verifies that content matches the transaction's real outputs, and verifies that the UTXO referenced in step 3 is genuinely the one being consumed. Only the minter's own key signs this transaction.

## 6. Lifecycle: withdrawal (XEC → Ethereum)

Unlike deposit, this direction has no separate Ethereum-side confirmation step — the burn transaction itself, plus proof of its inclusion in the XEC chain, *is* the entire authorization. The Authorizer participates only as a co-signer of that one transaction, in a role structurally identical to a ["post office" under the SLP Postage Protocol](https://github.com/badger-cash/slp-specifications/blob/master/slp-postage-protocol.md), not as a separate attestor.

1. **Burn construction.** The user constructs a transaction spending their wrapped-token UTXO(s), with an OP_RETURN that is a bridge-specific variant of the standard SLP Type 2 `BURN` format: the standard BURN fields (`token_id`, burn quantity) plus an additional field naming the `assetId` of the bridge/lock contract this withdrawal targets — the same role `assetId` plays on the deposit side (§9, §10). The user's SLP input(s) are signed with `SIGHASH_ALL | SIGHASH_ANYONECANPAY`, exactly as the Postage Protocol requires of the sender, so that further inputs can be appended without invalidating this signature.
2. **Postage.** Because SLP inputs and outputs are pegged at the 546-sat dust value, the transaction as constructed in step 1 doesn't carry enough value to cover its own miner fee (the same problem the Postage Protocol exists to solve). The Authorizer appends one or more of its own XEC "stamp" inputs to cover the fee, and signs those inputs itself with plain `SIGHASH_ALL`. The Authorizer does not touch, and cannot alter, the user's own burn input or the OP_RETURN content — it only contributes and signs its own separate input. This is the only signature the Authorizer ever produces in the withdrawal direction, and it doesn't sign anything that transmits the user's value (see the note on invariant 2, §3).
3. **Proof and release.** Once the postage-signed transaction from step 2 is broadcast and confirmed, the Authorizer's involvement is over — the user (or anyone) independently retrieves the confirmed transaction and its containing block from their own view of the XEC chain, constructs the Merkle path themselves, and submits transaction + header + Merkle path to the Ethereum lock contract. No further cooperation from the Authorizer, the bridge operator, or any specific indexer is needed to complete this step; nothing about it can be gated or delayed by anyone once the burn is confirmed. The contract: parses the transaction; validates both the user's signature over the burn and the Authorizer's signature over the stamp input; checks that the supplied header is internally self-consistent (its hash meets the difficulty it claims) and that difficulty clears a fixed minimum threshold; verifies the Merkle path against that header; extracts the `assetId`, token, and burn amount from the OP_RETURN; and, if everything checks out, releases the corresponding locked collateral (net of the fixed withdrawal fee) to the burner's own Ethereum address, derived cryptographically from the public key already present in the burn transaction's own scriptSig — the same Keccak-based derivation `buildOutOracle` already uses elsewhere, applied here to the burner's key instead of a caller-supplied one.

   The recipient can't be a caller-supplied argument to this call, even though that would be simpler: burn transactions are public on XEC before anyone submits the Ethereum-side claim, so a free recipient parameter would let anyone watching the XEC mempool front-run the real burner's claim with their own address. Deriving the recipient from the burner's own pubkey instead means whoever submits this call, and whatever address they'd prefer to receive funds, is irrelevant — the released funds only ever go to whoever actually held the burning key.

   This PoW check deliberately verifies only the one referenced header, not chain continuity back to a known point (no header-chain relay, no cumulative-work tracking). Its purpose is not to independently prove canonical-chain inclusion the way a full light client would — it's a second, cheap-to-verify factor alongside the Authorizer's signature. The Authorizer's signature is what actually gates release; the PoW floor means that even if that signature were ever compromised or misused, a fraudulent release would additionally require producing a header that clears real difficulty, which isn't free or instant to fake. Two independent things have to hold — a valid signature and evidence of real mining cost — rather than either one being sufficient by itself.

This is a materially different design from the oracle-signed "out" attestation currently implemented in `packages/sdk` (see §9), where an Authorizer-equivalent role signs a separate withdrawal *message*, disconnected from the actual token burn. Here, the Authorizer's participation is bound directly into the one transaction that does the burning, and Ethereum verifies that transaction's authenticity and on-chain inclusion directly rather than trusting a relayed message about it.

## 7. Security properties (summary)

- **Non-custodial throughout.** No party but the user ever holds a key capable of moving the user's locked or wrapped funds, in either direction.
- **Authorizer has no discretion.** On deposit, it cannot choose the amount, the recipient, or which deposit gets authorized — only *when* (subject to the fixed confirmation threshold) and *whether* to participate at all. On withdrawal, its only choice is whether to provide postage for a transaction whose burn content it doesn't construct and can't alter.
- **No double-authorization.** A given deposit can be confirmed at most once (invariant 6, enforced on Ethereum).
- **No double-redemption.** A given authorization can be minted at most once (invariant 7): it's bound to one specific vault UTXO, and that UTXO can only be spent once. This holds regardless of how many other UTXOs coexist in the vault to allow concurrent mints (§4).
- **A confirmation signature can't be used before its deposit is irreversibly confirmed.** This is *not* enforced by either chain's consensus or contract code — it depends entirely on the Authorizer following vault UTXO quarantine (`docs/SPEC.md` §III.7, §4/§5 above): the referenced vault UTXO must not exist on XEC until the corresponding Ethereum confirmation has reached finality. Without it, a signature observable before its `confirmDeposit()` call mines (e.g. via a public mempool) could be used to complete an unbacked mint even after the depositor front-runs it with a refund, since the signature's own validity has no dependency on that Ethereum call ever succeeding.
- **Refund now requires an announced cooldown.** `refund()` (§5 step 2) can only be called at least `refundDelay` blocks after a `requestRefund()` call, giving the Authorizer's monitor advance, observable warning of refund intent. This is defense-in-depth layered on top of, not a substitute for, the property above: it narrows the practical window for the race, but an already-extracted signature is only made harmless by quarantine, not by this cooldown.
- **Two-factor withdrawal release.** Release requires both a valid Authorizer signature (co-signing the burn as postage provider) *and* a Merkle proof against a block header that independently clears a minimum proof-of-work floor. Neither is sufficient alone: the signature without real PoW behind it doesn't release funds, and a header meeting the floor without a valid Authorizer signature doesn't either. This is deliberately not a full trustless light client (no header-chain continuity is checked, §6, §10) — the Authorizer's signature remains the primary trust anchor, and the PoW floor is a supplementary factor that raises the cost of a fraudulent release if that signature is ever compromised or misused, rather than an independent security guarantee on its own.
- **Independent verifiability.** Anyone — not only the bridge operator — can recompute the expected authorization content from public deposit data and confirm the Authorizer's signature matches it, without trusting an out-of-band claim about which contract deployment or which asset is in play. This is why `assetId` (in `BridgeAssetConfig`) must be the lock contract's own address rather than the bridged token's contract address — see the SDK README for the reasoning. The same `assetId` scopes withdrawal burns to the correct bridge deployment (§6).
- **Withdrawal completion needs no ongoing cooperation from anyone.** The Authorizer's only involvement in a withdrawal is co-signing the burn transaction once, as postage provider (§6 step 2). After that transaction is broadcast and confirmed, claiming on Ethereum requires only the user's own (or anyone's) independent view of the XEC chain to retrieve the transaction and its block and construct a Merkle path — no API, indexer, or party's continued participation is needed, and none of them can gate or delay the claim.

## 8. Component mapping

| Component | Repo location | Responsibility |
|---|---|---|
| Ethereum lock contract | `packages/contracts` | Lock/refund, deposit recording, Authorizer confirmation + deterministic content computation + signature verification, deposit-confirmed tracking; on withdrawal, parsing the burn transaction, validating both signatures on it, verifying its Merkle inclusion against a header meeting a minimum PoW threshold, and release |
| eCash primitives | `packages/sdk` | Self-mint covenant construction/parsing, mint transaction building from Ethereum-sourced content, genesis and vault funding, burn+postage transaction building, address/config management |
| Authorizer service | not yet a package | Watches Ethereum for deposits, applies the confirmation-depth threshold, submits confirmation calls; on withdrawal, co-signs burn transactions as postage provider. Doesn't exist as code yet in either package — likely its own service/package once the contract interface above is settled |

## 9. Deltas from the current SDK

This is the actionable part of this document — concretely, what in `packages/sdk` today does not match the design above, for follow-up.

- **The oracle "out" attestation mechanism doesn't belong in the final design.** `buildOracleOutTx`, `buildOutOracle`/`buildOutOpReturn`/`parseOutOracle`, and `toOracleRing('out', ...)` all model an Authorizer-signed withdrawal *message*, disconnected from the actual token burn. Per §6, the Authorizer's only withdrawal-side role is co-signing the burn transaction itself as a postage provider. These are candidates for removal.
- **Resolved, partially: a burn/postage transaction builder now exists, but only inline in `packages/contracts`' own tests, not as a first-class `packages/sdk` export.** `packages/contracts/test/helpers/ecash.js` and `test/release.test.js`/`test/e2e.lifecycle.test.js` build and sign the user's half (an SLP `BURN`-variant transaction carrying `assetId`, signed `SIGHASH_ALL | SIGHASH_FORKID | SIGHASH_ANYONECANPAY`) and the Authorizer's half (a postage stamp input, `SIGHASH_ALL | SIGHASH_FORKID`, per the SLP Postage Protocol) directly against real eCash primitives, proven against a deployed `BridgeLock.release()`. Still open: promoting this to an exported `packages/sdk` function, the way `mintCovenantV2` exists for the deposit side.
- **Resolved: Merkle inclusion and minimum-PoW header verification now exist**, in `packages/contracts` (`lib/MerkleProof.sol`, `lib/Difficulty.sol`), cross-validated against an actual mined XEC block (`test/lib.realblock.test.js`) as well as against `packages/sdk`'s own `buildMerkleProof`.
- **Resolved: the self-mint covenant no longer deconstructs a prior oracle attestation transaction.** `mintCovenantV2` (`packages/sdk/src/script.ts`) replaces `mintOutscript` (still present, unremoved, for the legacy path) exactly as described below: it verifies a direct Authorizer signature over a compact message, the same way it already verifies the minter's own signature, with no transaction-deconstruction logic. See `docs/SPEC.md` §III.6 for the current design; `mintOutscript` itself has not been deleted from `packages/sdk/src/script.ts`, so both covenant versions currently coexist in the codebase.
- **The CTRL OP_RETURN "in" format is tied to the broadcast oracle "in" transaction and likely becomes unnecessary** once that transaction no longer exists — the content it currently encodes would instead come from Ethereum directly.
- **Nothing yet funds the vault beyond genesis's single UTXO — but this is a funding-strategy gap, not a covenant-logic gap.** An earlier draft of this document assumed Type 2 required "chaining" a single vault UTXO forward through each mint, the way Type 1's MINT Baton worked. That's backwards: Type 2 was specifically designed to *remove* that requirement (§4) — `mintOutscript` already accepts any qualifying UTXO at its own address, with no changes needed there. What's actually missing is a way to keep the vault stocked with more than one spendable UTXO at a time, since today the only UTXO ever sent there is the single one `buildGenesisTx` creates. Once the Authorizer stops broadcasting a fresh single-use "stamp" per deposit (which is what currently, incidentally, keeps a UTXO available for each mint), something needs to replace that — either batch pre-funding or self-replenishing mint outputs (§4, §10).
- **`buildGenesisTx`'s funding output doesn't currently go to the vault address at all.** Its `mint_vault_scripthash` OP_RETURN field is correctly set to the covenant's own scripthash, but the actual funded UTXO it creates (output 1) is sent to the oracle's own ring address (`oracleKeyring.getAddress()`), not to `Address.fromScripthash(outscript.hash160())` — because in the current design that UTXO's job is to fund the oracle's *next attestation transaction*, not to seed the vault. If the ring mechanism goes away (see below), this output should instead fund the vault directly.
- **Type 2's multi-output MINT capability is unused.** The spec explicitly allows multiple outputs on one MINT transaction (unlike Type 1) and suggests non-custodial fee outputs as a use case. Today's `buildOracleInTx`/`buildMintTx` only ever produce one recipient output. Worth considering deliberately, both for a vault-replenishment output (above) and for any protocol fee on the XEC side.
- **`toOracleRing`'s "in" ring may no longer be needed at all.** Its purpose was to give the Authorizer's own attestation-broadcasting transaction a P2SH address to be funded and spent from. If the Authorizer never broadcasts an "in" attestation to XEC, there's no transaction left that needs that address — the Authorizer's public key can likely be consumed directly by `mintOutscript` (as it already is today, via `authPublicKey`) without the surrounding ring/address machinery. Whether `genesis` still needs it, or can move to a plain key, is an open question (§10).
- **Resolved: confirmation-depth logic now exists**, enforced on-chain in `BridgeLock.confirmDeposit` (`minConfirmations`, a constructor-fixed parameter — `docs/SPEC.md` §III.3).
- **`BridgeAssetConfig`'s explicit-config design (no env vars) and `assetId`-as-lock-contract semantics already match this document** and don't need to change.

## 10. Open questions

- Does the genesis flow still need the "oracle ring" P2SH scripting (`networkId`/`assetId`/pubkey baked into a redeem script), or can it move to a plain key now that it's a one-time administrative action rather than a per-deposit attestation?
- **The Authorizer now clearly needs to run an eCash wallet** — it has to hold and manage its own stock of XEC "stamp" UTXOs to act as postage provider on withdrawal (§6), the same way the Postage Protocol spec itself recommends post offices keep "an available stock of stamp UTXOs, of one or more standardized weights." That resolves part of the earlier open question about whether the Authorizer needs XEC-side key material at all — it does. What's still open is whether that same wallet/UTXO set is also what's used to fund the mint vault (§4, §9), or whether those are kept operationally separate. **Resolved as a requirement, regardless of that choice: whatever process funds the vault must respect vault UTXO quarantine** (`docs/SPEC.md` §III.7) — the Authorizer must be able to construct a vault-funding transaction, know its txid, and hold it unbroadcast until the confirmation it backs has reached Ethereum finality. This is now a hard constraint on the Authorizer service's design, not an open question itself.
- **Resolved: single-header floor check, no chain-continuity verification.** The contract checks that the one referenced header is internally self-consistent and clears a fixed minimum difficulty; it does not track cumulative work or verify the header extends the real XEC chain. This is intentional, not a simplification taken for lack of a better option: the PoW check is meant as a second factor alongside the Authorizer's signature (§7), not as an independently-sufficient trustless inclusion guarantee, so it doesn't need the strength a full light client would provide. Still open: what the actual minimum difficulty value should be, and whether it's a hardcoded constant or governed some other way (subject to invariant 4 — no administrative override, so "some other way" would need its own non-discretionary mechanism if used at all).
- What exactly is the byte layout of the `assetId`-extended BURN OP_RETURN — appended after the standard Type 2 BURN fields, and would a standard SLP indexer that doesn't know about the extension still correctly index the burn, or does the extra field need to live somewhere that doesn't confuse existing tooling?
- Should the Authorizer service be its own package (`packages/authorizer`) once its interface is settled, given it's neither purely eCash-side nor purely Ethereum-side?
- Batch pre-funding vs. self-replenishing mint outputs for the vault (§4, §9) — which, or both? Self-replenishing keeps the vault stocked automatically but ties vault health to mint volume; batch pre-funding decouples them but needs its own operational process and monitoring for when the vault runs low. Either choice must independently satisfy vault UTXO quarantine (§4, `docs/SPEC.md` §III.7) — self-replenishing outputs are naturally quarantine-compatible (a mint's own change output only exists once that mint transaction itself is broadcast, which never happens before its authorizing confirmation landed); batch pre-funding needs the withhold-the-whole-batch discipline described in §4 above.
